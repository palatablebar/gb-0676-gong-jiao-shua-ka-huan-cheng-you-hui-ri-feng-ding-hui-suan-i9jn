# 历史批次复算裁决与模型

## 一、问题

票价规则更新后重跑上月刷卡，复核员只能看到一套按当前规则算出的结果，分不清差异来自**补录/数据纠错**还是**规则变化**；而若为复现原账长期锁住旧规则，后来确认的数据错误又无法纠正。

## 二、裁决（不是二选一，而是双账分工）

1. **原账按乘车发生时的规则原样重现，并冻结为不可改写的历史证据。**
   规则登记簿（`app/rule_registry.py`）按生效窗冻结每一版完整规则集；`rule_mode=as_of` 依据刷卡时间选取当时生效版本，原账因此可被随时重新复算，而不需要在系统里长期“锁住”一份会阻止纠错的活规则。
2. **复算账按当前规则重出，同时保留原账。**
   `rule_mode=current` 用最新规则重出；补录或更正后的输入同样走当前规则重出。原账一行不改，纠错在新版本中体现。
3. **每个业务批次只有一个当前生效结论，并附可追溯的规则变化说明。**
   批次头 `current_run_id` 唯一指向当前结论，可在版本间切换（乐观锁）；每版记录规则版本、规则集指纹与相对上一版的结构化差异（票价、换乘优惠、封顶参数）。

**为什么不是单纯 A 或 B：** 只按旧规则重现，确认的数据错误无法纠正；只按当前规则重出，历史结论不可复现、责任无法界定。双账并行让“历史是什么样”与“现在该怎么认”各归其位，差异来源可区分、可追溯。

## 三、差异归因（同一来源对照）

`app/attribution.py` 以 `event_id` 与 `_sources` 来源行为同一线索，逐行对照原账与复算账：

| 归因 | 判定 |
|---|---|
| `DATA` 补录/数据纠错 | 来源行集合变化、采纳/隔离状态翻转或原始字段变化，规则版本相同 |
| `RULE` 规则变化 | 输入完全一致，仅规则版本不同导致金额变化 |
| `MIXED` 双重变化 | 输入与规则同时变化，避免把数据错误误记为规则影响 |

批次级另给应扣总额差、仅原账/仅复算的来源行。

## 四、约束与落地位置

| 要求 | 落地 |
|---|---|
| 同一来源对照原账、复算账与变化原因 | `/api/batches/<ref>/compare` 与 `/recalc` 页面三栏对照 |
| 同一批重试不新增版本 | 账本以 `attempt_id = run_id`（输入+规则+参数指纹）唯一，重复提交复用原版本 |
| 版本切换失败仍可读取完整旧版 | 切换仅更新批次头指针，旧版完整 payload 永久保留；陈旧切换 409 |
| 来源未对平前不得封存日结 | `store.seal` 校验当前版本 `balanced`，未对平返回 422 |
| 原始输入与规则依据留档 | 清单保存 `input_raw_base64` 与 `rule_basis`；证据 CSV 含 `RAW_INPUT`、`RULE_BASIS` 段 |
| 误删不断复算链 | 无删除接口（DELETE 405）；`/verify` 重算哈希链检测篡改与断链 |

## 五、数据模型

- `runs`：每次计算的完整结果（沿用，含乐观锁 `version` 与复核 `decision`）。
- `batches`：业务批次，`current_run_id` 为唯一当前结论，`sealed` 标记封存。
- `batch_versions`：只追加账本，含 `ledger_version`、输入摘要、规则版本与指纹、`prev_hash`、`chain_hash`。
- 哈希链：`chain_hash = sha256(prev_hash || 规范JSON(payload))`，首版前驱为 `GENESIS`。

## 六、演示路径

1. 用 `month_legacy.csv` 以 `as_of` 建立十月批次原账（r1：F1=2.00、换乘优惠1.00）。
2. 同输入切 `current` 重出：差异全部归因为 `RULE`，应扣总额随换乘优惠下调而增加。
3. 用 `month_corrected.csv`（补录 0112、更正 0190 线路）以 `current` 重出：新增来源行与混合差异归因为 `DATA`/`MIXED`。
4. 在 `/recalc` 页面切换当前结论、校验哈希链，对平后封存；封存后任何复算被拒绝。
